# Doctor Calendar & Appointments demo

Open `/doctor` and use the existing Calendar sidebar item. My Availability edits the recurring Sunday–Saturday schedule. Initial Sunday–Thursday hours are illustrative only. Add/remove intervals, choose workplace and duration, then save. Exceptions close a whole local date and are saved with the weekly configuration. Slot preview uses the saved schedule, not unsaved form values. All dates/times are in `Asia/Amman`; native inputs represent wall-clock times in that zone.

Appointment requests must originate from the future Mother booking flow. The Doctor UI cannot generate them and no requests are seeded automatically. Existing requests remain reviewable; the pending count and bell use the same state. Approve/reject still require confirmation, and rejection requires a reason.

Previously generated requests used random UUIDs with no dedicated demo marker. They cannot safely be removed automatically based on a child name or reason. For a manually confirmed test request only: back up the exact doctor-scoped storage payload in DevTools, identify the exact request ID using its date/time and reason, remove only that object from the requests array, preserve availability, exceptions, every other request and version, increment revision, then refresh all open doctor tabs. Never clear the whole key or match all requests for a child. Browser storage was not changed by this cleanup.

## Reusable interface

`appointmentsData.js` has no React dependencies. `initialAvailability(doctorId)` returns weekly hours and exceptions. `availableSlots(availability, requests, YYYY-MM-DD, now)` returns bookable slots with stable doctor/time identifiers and absolute ISO `start`/`end` timestamps. `submitBooking(state, { id, doctorId, childId, start, end, reason }, now)` rechecks the slot and returns a new state and pending request or an error. Requests snapshot workplace/location so editing a schedule never rewrites existing bookings. `decideBooking` rechecks availability and reservations, permits one pending-to-approved/rejected decision, and records `decisionAt` and rejection reason. Pending/approved reserve time; rejected/cancelled release it. There is no automatic expiration of pending requests. `saveAvailability` rejects changes that exclude future reservations and returns the conflicting requests; it never cancels anything.

For the future Mother flow: obtain her server-authorized linked children, select a child and doctor, query available dates/slots, collect the reason and call `submitBooking` with a stable request UUID. Mount a coordinated shared provider/repository above the routes so both dashboards consume one state; do not create a separate independently writable booking copy. The current hook is owned by DoctorDashboard only. No Mother files or shared routes were changed in this step.

## Persistence and safety limits

Dedicated key: `nomu.doctor.demoBookings.v1.<encoded-doctor-id>`. Payload includes version, revision, availability, exceptions, requests, statuses, and decision metadata. The default mock doctor ID is `demo-doctor-sarah-ahmad`. Saving a schedule or request persists immediately; refresh restores it. Empty initial configuration is illustrative until first save. Invalid storage remains untouched and produces a warning. Write failures do not report successful saves. Revision checks reject known stale-tab writes and ask for refresh; localStorage is not an atomic multi-client booking system. It does not synchronize across accounts, browsers, or devices. No real patient or medical information belongs here. Existing follow-up appointment keys and medical records are untouched.

Medical follow-ups remain a separate clinical model: those may lack a time, end time, or doctor ID. They are not silently converted into bookings or counted as slot reservations. A future backend integration must reconcile the two explicitly. Approved booking cancellation/rescheduling is not implemented here; conflicting availability changes must be reverted or await a coordinated cancellation/rescheduling flow. No booking is silently changed.

Backend requirements: stable authenticated doctor IDs; mother–child authorization; doctor access checks; server-side timezone/calendar rules; transactional overlap prevention covering pending and approved reservations; decision audit fields derived from the authenticated actor; optional pending expiry policy; idempotent submissions; persistent database; approved cancellation/rescheduling policy; and event/polling notifications. Browser controls and revision checks provide no real authorization or concurrency guarantee.

Run `node src/components/doctor/appointments.check.mjs`, the existing doctor check scripts, `npm run lint`, and `npm run build`. Automated checks exercise pure logic, persistence, and server-rendered Arabic/English markup; live browser interaction and visual layout require a connected browser.
